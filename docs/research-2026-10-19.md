# Helicoid improvement research

**Level: L3. Scope:** native Mac and Windows Manager/Computer applications, their shared media boundary, and setup/reliability. Research and local source review on **19 October 2026**. No application, infrastructure, DNS, account, or permission changes were made.

## Brief and constraints

**User constraints:** research improvements to both appearance and behavior; use **Context.dev exclusively for online research**. Preserve the native Swift and WinUI applications, supplied artwork, existing product decisions, and unrelated changes. Keep the accepted explicit-control behavior, optional-by-default operator MFA, mandatory administrator MFA, and hosting/platform scope. Sharing, attention, files and other unfinished version 1 tools remain separate work.

**Assumptions:** “the software” means Helicoid in this workspace. The audience is its owner and the engineers selecting the next implementation packages. This is a recommendation, not authorization to change product behavior or evidence that a release is ready.

The research sequence was native interface guidance, capture/input and connection reliability, then cross-checking recommendations against the actual source and accepted evidence. Official documentation establishes platform capabilities; it does not establish that Helicoid implements them.

## Executive answer

Helicoid will improve most by completing a smaller set of everyday workflows and giving each state a clear, compact native presentation. The next design pass should connect status to useful actions, simplify the Computer app, and make previews dominate the Manager. It should also fix concrete application wiring gaps rather than merely restyle placeholders.

The main functional priority remains **trusted connection → endpoint admission → actual capture → real preview → explicit control**. The native bridge still returns unavailable for capture, admission and frame acquisition. Neither a successful build nor a connected WebRTC laboratory peer substitutes for that chain.

Recommended order:

1. Fix the Windows Computers presentation and normal trusted-profile startup.
2. Simplify Computer status/permissions and establish reusable native presentation rules.
3. Complete one real admitted Mac Manager → Windows Computer preview path, with diagnostics and bounded resource use.
4. Add independent Mac detail windows and the explicit control lifecycle; repeat across all four combinations.
5. Finish hosting, update/recovery and installed acceptance, retaining the existing production gates.

UI work can proceed alongside the engine package when file ownership is independent. Do not enable closed capabilities merely to make a screen look complete.

## Appearance and interaction findings

### U1. Make Computer status a small, useful summary

**Observed:** the Mac menu is already a native menu, with connection/access status and actions. Its separate status window still contains Help fields, permission cards, repeated screen-access explanation and a long control-policy paragraph. The Windows Computer window exposes Supervisor, Worker and Generation beside repeated access information, permanently disabled actions and repeated control-policy copy. See [Mac Computer UI](../apps/macos/Sources/HelicoidComputer/HelicoidComputerApp.swift) and [Windows Computer UI](../apps/windows/src/Helicoid.Computer/MainWindow.xaml).

**Recommendation:** make the first view answer three questions: connected to which deployment, is anyone viewing/controlling, and does anything need attention? Use one familiar icon plus a short state label. Show authenticated operator names while access is active. Keep deployment identity available. Move supervisor/worker/generation, logs and policy explanation into Details. Remove unfinished Help controls from the ordinary layout until their real service exists; this does not implement Help or alter who may stop control.

Keep the menu small: state, Open Status, Settings and Quit. Use the larger status view for recovery actions. Preserve trusted disclosure and its required liveness; reduced copy must not conceal active observation or control.

**Acceptance:** normal/offline/observed/controlled/permission-missing states have an unambiguous first view; actual operator identity is accessible; no disabled Help form dominates the window; diagnostics remain available. Review on both OSes, rather than copying Mac pixels into WinUI.

### U2. Fit permission settings to their content and make recovery actionable

**Observed:** current Mac Settings uses a fixed `600 × 400` frame for two rows. It now has native bordered Allow buttons with explicit `Color.primary` and no per-row gear buttons. The previous screenshot's black-label defect is therefore **not established as a current source defect**. The evidence explicitly leaves replacement visual contrast unverified. Permission queries and request actions are real native API calls, but this is current-process readiness, not proof of the future capture worker's permissions. See [permission UI](../apps/macos/Sources/HelicoidComputer/HelicoidComputerApp.swift), [native probe](../apps/macos/Sources/HelicoidComputer/ComputerPermission.swift), and [status model](../apps/macos/Sources/HelicoidComputer/ComputerStatusModel.swift).

**Recommendation:** retain the Manager setup's restrained titlebar, system background and spacing, but size the permission pane around its actual content. Use icon, permission name, short role label, status and one next action. Do not restore gear buttons. If runtime testing shows that another Allow request cannot advance a denied permission, expose a contextual text action to the appropriate System Settings pane. Re-query when returning; never optimistically mark a permission granted. Do not invent a denied/restart-required state from a Boolean probe.

Apple says macOS Settings windows accommodate the current pane, retain the standard menu/keyboard entry point, and use an appropriate title [S1]. System colors and measured contrast support appearance and accessibility settings [S2]. These support a compact native layout, not a mandatory exact window size.

**Acceptance:** packaged app screenshots in light/dark appearance, active/inactive windows and Increase Contrast; keyboard/VoiceOver reach both actions; no clipping at larger text; grant, denial, return from System Settings and revocation show truthful results. Worker readiness must be measured in the actual worker context once it exists.

### U3. Put previews and selection ahead of toolbar machinery

**Observed:** Mac's toolbar contains layout, preview size, status, inclusion and an Actions menu with unfinished tools. Windows leads with disabled Share/Message, file-related menu entries, Grid, Clear Selection, Pause and manual inventory loading, followed by a visible development-fixture toggle. Some Mac empty-state copy explains implementation details, including “Nothing is invented here.” See [Mac Computers](../apps/macos/Sources/HelicoidManager/Views/Computers/ComputersView.swift) and [Windows Computers](../apps/windows/src/Helicoid.Manager/Views/ComputersPage.xaml).

**Recommendation:** keep Computers, search, the selected/displayed scope, and available preview actions prominent. Use a compact layout control and contextual Pause/Resume. Put infrequent filters/size preferences into an appropriate secondary surface; keep common actions discoverable. Move development-only controls outside the ordinary user workflow while preserving explicit fixture labeling. Gate unfinished modules by actual capability instead of exposing dialogs that only explain that they cannot run.

Use actionable empty states: No enrolled computers → enrollment/admin path; Nothing included → Choose Computers; No matches → Clear Filters; Permission missing → named recovery; Unsupported build → one concise explanation. Distinguish ordinary recoverable unavailability from an unsupported capability.

Apple and Microsoft both prioritize important tasks in toolbars [S3, S10]. Veyon's thumbnail overview and separate remote-detail workflow are a useful interaction reference [S9], without adopting its classroom terminology or unrelated features.

**Acceptance:** full keyboard route from search to selection to View Screen; clear target count; no toolbar clipping in the minimum supported window; All/inclusion/filter/selection semantics stay unchanged. Ordinary UI contains no developer transport terminology.

### U4. Make preview state richer than Online/Offline

**Observed:** Mac tiles present host status separately from admission placeholders; an admitted placeholder says “Preview requires engine.” Windows has a separate readiness placeholder model. Neither represents delivered production frames yet.

**Recommendation:** define shared state meanings, rendered natively: connecting, waiting for permission/user, view-only live, paused, stale, disconnected and denied. Keep host reachability, observation readiness and control ownership separate. A stale indication should include a meaningful receiver freshness measure; authorization loss must clear pixels immediately. Use labels/icons alongside color. Keep technical causes available in Details.

**Acceptance:** demonstrate each transition using an actual integrated build. An online host never implies a live stream; a DTLS connection never implies admission. No old frame remains after authorization or desktop invalidation. Unknown states remain explicit.

### U5. Establish a small native UI contract and test the finished pixels

**Recommendation:** agree on spacing, text hierarchy, card density, SF Symbols/Fluent icon roles, selection treatment and semantic states. Share behavior and vocabulary across platforms, with platform-native controls and chrome. Avoid introducing a large custom component system for two permission rows.

The successive user screenshots demonstrate why source/build tests alone are insufficient. Keep reference screenshots for Computer Settings, status/menu, Manager empty/populated grid, detail view and setup. Check light/dark, inactive windows, contrast, keyboard focus, VoiceOver/Narrator, display scaling and long names. Apple specifically recommends system-defined colors and contrast checks [S2].

**Acceptance:** visual evidence names the exact artifact/revision; no claim of visual completion based solely on `.foregroundStyle`, a snapshot fixture or compilation. Keep supplied artwork unchanged.

## Functional and reliability findings

### F1. Complete Windows Computers rendering before polishing its tiles

**Confirmed source gap:** `MainViewModel.Tiles` is an observable collection populated by inventory loading. However, `TileHost` has no `ItemsSource`, item template or code-behind population. The Grid/List handlers change `IsGridView`; no presentation in the Manager consumes that property. The tile host is also in an Auto-height row rather than the page's remaining-space row. See [XAML](../apps/windows/src/Helicoid.Manager/Views/ComputersPage.xaml), [code-behind](../apps/windows/src/Helicoid.Manager/Views/ComputersPage.xaml.cs), and [view model](../apps/windows/src/Helicoid.Manager/ViewModels/MainViewModel.cs).

**Recommendation:** bind inventory to a real selectable grid/list, consume filtering/display state correctly, wire activation and selection, and use an appropriately bounded/virtualized scrolling surface. Move the inventory load into the authenticated lifecycle, with Refresh as a secondary action rather than a prerequisite the operator must discover.

**Acceptance:** native Windows app loads an authorized inventory, displays the correct names/count, changes grid/list visibly, filters/selects correctly, opens details and clears inventory on expiry. Include one UI integration test so domain-model tests cannot pass while the page stays unwired. This review did not run the Windows app, so the visible runtime symptom remains unverified.

### F2. Connect normal startup to real trusted profiles

**Observed:** the Mac app constructs `ManagerSession(configuration:)` without its optional production authentication client. The session defaults to `UnavailableConnectionClient` outside explicit development/fixture routes. The normal production entry point therefore remains closed despite tested auth components. See [app startup](../apps/macos/Sources/HelicoidManager/HelicoidManagerApp.swift) and [session construction](../apps/macos/Sources/HelicoidManager/ManagerSession.swift).

**Recommendation:** finish independently trusted profile adoption, device-key creation/storage, pending-manager approval, native sign-in/MFA and session restoration/expiry as one normal onboarding path. Preserve admin/operator/recovery assurance rules. Importing a URL or discovering a server must not establish trust. Preserve the existing fail-closed behavior until this composition is verified.

**Acceptance:** launch the packaged app without fixture/development switches, import a genuinely authenticated enrollment/profile artifact, approve the actual device and load authorized inventory. Wrong trust, pending/revoked device, expired session and recovery-only credentials must deny observation/control.

### F3. Build one real admitted preview as the next end-to-end milestone

**Observed:** `hs_capture_begin`, `hs_admission_begin` and `hs_media_frame_acquire` still return `HS_STATUS_UNAVAILABLE` at the end of [the native bridge](../modules/core/webrtc-native/native/hs_webrtc_bridge.cpp). The apps accurately expose that boundary. Connection-only checks are useful prerequisites, not a working media bridge.

**Recommendation:** complete Mac Manager → Windows Computer, one physical-console display, through the actual engine-issued verified channel, actual approved identities, durable admission and real worker. Then expand the same interfaces across combinations. Retain generated ABI/wrapper drift checks, owned frame release, close/callback drain and independent receiver limits. Keep audio, clipboard, files and forwarding disabled.

**Acceptance:** real pixels from a separately running endpoint; denial before admission and after revocation; malformed frames rejected; no held frame survives disposal incorrectly; slow receiver does not stall others. Record exact binaries and OS effects. Do not substitute a laboratory grant or fixture identity.

### F4. Use independent remote windows and an explicit control state machine

**Confirmed source mismatch:** Mac opens remote detail through a `.sheet` inside the grid and renders only `openRemoteWindows.first`. The list context menu appends an ID but the sheet presenter lives in the grid. This does not provide the specified independent per-computer windows. The remote view's control button is intentionally unavailable. See [grid/list presenter](../apps/macos/Sources/HelicoidManager/Views/Computers/ComputersView.swift), [window IDs](../apps/macos/Sources/HelicoidManager/ManagerSession.swift), and [remote content](../apps/macos/Sources/HelicoidManager/Views/Remote/RemoteViewWindow.swift).

**Recommendation:** use native windows keyed by computer/session with their own observation lifetime, display picker and view-only starting state. Make Control Requested, Controlling and Pending Release explicit. Require reservation plus endpoint acknowledgment. Focus loss stops forwarding and cleans held input; minimize releases/cancels control; restore/reconnect remain view-only until Take Control. Closing one viewer must not end another observer.

**Acceptance:** open two computers from grid and list, move windows independently, close the main window, compete for control, minimize during a pending claim, interrupt release acknowledgment, and reconnect. Verify actual endpoint input effects and generation-safe cleanup. Do not clear Pending Release simply because the UI closed.

### F5. Treat platform readiness as a live capability, not a startup checkbox

**Recommendation:** connect capture, permissions, signed-in physical-console identity, worker generation and trusted disclosure to one continuously enforced readiness model. Windows capture/input belongs in the eligible user's worker; the service supervises it. Missing ScreenCaptureKit/Accessibility permissions must disable the affected capability truthfully. Keep a surviving, generation-scoped cleanup path.

Microsoft documents session-0 isolation and recommends a separate interactive-user process with secured IPC [S7]. `SendInput` can fail under UIPI without identifying UIPI as the cause and does not reset existing key state [S6]. Therefore report unsuccessful input honestly; do not infer an exact failure cause from insufficient evidence or release physical keys indiscriminately. Windows capture support also needs an actual API check [S11].

**Acceptance:** installed-device lock/logout/switch/RDP, UAC/integrity boundaries, permission revocation, display changes, worker crashes and disclosure loss. Include local/injected modifier overlap and partial input insertion. A VM/domain test cannot establish physical-console acceptance.

### F6. Measure freshness and apply backpressure before pursuing higher quality

**Recommendation:** instrument capture, encode, receive, decode and presentation independently. Carry sequence/generation metadata and use monotonic local deadlines. Track latest valid frame/heartbeat age, queue pressure, dropped frames and delivered dimensions/rate. Treat “nothing changed on the desktop” separately from “capture stopped”; receiver frame age alone can misclassify static content. Do not equate RTT or WebRTC freeze counts with input-to-visible latency.

Use two bounded operating profiles: low-rate overview and higher-rate detail. Configure capture dimensions/frame rate upstream, not only by shrinking a full-resolution image in the UI. Keep native capture-buffer depth separate from Helicoid's bounded latest-frame handoff per receiver. Apple's sample documents the memory trade-off of ScreenCaptureKit queue depth [S4]. W3C defines useful video counters and a specific freeze heuristic, which must be interpreted in context [S5]. Availability in Helicoid's pinned native build must be checked before relying on any field.

**Acceptance:** measure the existing 30-preview freshness target, 1080p30 detail/input-to-visible target and eight-hour stability target on named hardware. Exercise a static desktop, busy video, slow receiver and bandwidth constraints. Record CPU, memory, bandwidth, freshness and failure behavior; do not claim fleet capacity from synthetic load. Keep software VP8/CPU handoff as the initial baseline; evaluate hardware acceleration only after a measured bottleneck.

### F7. Add a connection doctor that names the failed stage

**Recommendation:** show simple stage-specific recovery for deployment trust, authentication, manager approval, endpoint readiness, signaling, direct/relay connectivity and media delivery. Put selected route, technical reason and redacted diagnostics in Details. Offer bounded Retry/Run Check/Save Report actions, not a generic reconnect spinner or raw ICE text.

TURN is a normal requirement when direct connectivity is unavailable [S8], but configuration alone is not evidence of blocked-UDP/TCP443 operation. The supplied single-VM route remains a candidate in the evidence ledger. Do not represent it as public support, mutate the occupied proxy, or weaken actual allocation-expiry requirements based on this research.

**Acceptance:** fail each stage deliberately; the UI points to the right action without revealing credentials or granting new trust. Test direct and relayed paths, renewal interruption, edge/authority loss and both peers with UDP blocked. Reconnect obtains fresh authority and never restores queued input/control.

### F8. Make setup promise only what it can deliver

**Observed:** the Mac wizard collects several setup sections before explaining in Review that installation is unavailable. Server documentation keeps Windows/macOS installation closed. See [Mac wizard](../apps/macos/Sources/HelicoidManager/Views/Setup/GuidedSetupView.swift) and [server capability status](../modules/server/README.md).

**Recommendation:** establish route/package availability before collecting administrator/recovery details. Keep host checks, conflicts and review of actual owned changes. Connect all native clients to the single server-owned journaled installer contract. On Mac, use Service Management's registration/approval status and keep user-session capture separate from the authority daemon [S12]. A registered helper, running process or reachable port alone must not produce Deployment Verified.

Expose Server Ready for Enrollment and Deployment Verified distinctly. Make interrupted install/repair/update/removal recoverable without deleting data; keep backup verification, quarantined restore and reviewed cutover visible in operations. Correct obsolete RustDesk-first documentation when the relevant implementation package is accepted; the top-level README/decision documents currently lag the newer WebRTC evidence.

**Acceptance:** occupied-host tests for every route, approval denial, interrupted install/update, keep-data removal, security-floor rollback rejection, encrypted restore and two-actual-host cutover. Preserve the supplied VM's services and ports 80/443. Signing, installed acceptance and independent review remain release requirements.

## Contradictions and limits

- **Old screenshot versus current source:** the gear removal/button-color source change is present. It needs actual packaged visual confirmation, not another speculative button rewrite.
- **Grid/List property versus working layout:** domain/view-model support exists, but the Windows page lacks the presentation wiring. A green model test does not settle that integration.
- **Remote “window” naming versus lifecycle:** the Mac source names remote windows but presents the first ID in a grid-owned sheet. Verify the actual native window behavior after correction.
- **Connection proof versus product proof:** engine connection tests and authentication prerequisites coexist with explicitly unavailable media/admission exports. Keep both statements; neither cancels the other.
- **Planning drift:** older root documents still describe RustDesk adoption; current evidence and the user's accepted finishing direction select Google WebRTC. Treat RustDesk evidence as historical, not an alternative route to silently re-enable.
- **Provider interruption:** the first three searches succeeded after correcting a minimum-result parameter. Context.dev then returned `Unknown tool` for search/scrape/answers. After the user requested another attempt, search and all twelve selected page reads succeeded. Online work stayed within Context.dev. No provider credit count was reported, so none is inferred.
- **Not performed:** fresh native builds/tests, live UI inspection, capture/input, permission prompts, VM/DNS changes, network experiments, signing or performance measurements. User screenshots are historical examples, not fresh evidence of the current executable.

**Result:** source findings and source-backed recommendations **VERIFIED within this review's stated scope**. Installed behavior, current pixel appearance, performance and production readiness **NOT VERIFIED**. The report identifies the tests needed to close those gaps; it does not mark them passed.
