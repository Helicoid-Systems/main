### How Veyon handles desktop access

Each monitored computer runs its own Veyon Server. Its local VNC capture backend supplies screen data through that process. The documented internal backend listens on localhost; the manager reaches the network-facing Veyon Server. Veyon's configuration separately defines authentication and access rules. Its documented Windows backend is a lightweight UltraVNC implementation with a Desktop Duplication option. [Configuration reference](https://docs.veyon.io/en/latest/admin/reference.html#network-port-numbers), [platform notes](https://docs.veyon.io/en/latest/admin/platform-notes.html#ultravnc-server-settings).

The inspected client uses LibVNCClient/RFB framebuffer updates. It can request incremental or full updates, configure update intervals and encodings, and scale its received framebuffer for a thumbnail. Lower image-quality settings permit JPEG; the highest setting selects different encodings and disables JPEG. This is not evidence of a distinct reduced-resolution stream produced on the endpoint for every thumbnail. Remote viewing and control use the VNC view with an explicit view-only state.

Presentation has its own DemoServer path: consume updates from a local VNC backend, retain a sequenced update queue, and serve multiple receiver connections with bandwidth/quality adjustment. Its existence shows that fleet previews, interactive assistance, and one-source presentation deserve separate workload designs.

### Proposed feasibility sequence

1. **Native integration:** pin the test revision and dependency/build inventory. Produce an actual Mac native viewer for one Windows desktop, then a WinUI 3 viewer using the same narrow interface. Record real exports, buffer ownership, callback threads, cancellation, errors, and teardown. A Flutter window or ordinary RustDesk app launched externally does not satisfy this result.
2. **Admission and lifecycle:** demonstrate endpoint-enforced observation/control permission, two independent viewers, one controller, denial before pixels/input, visible operator identity, expiry/revocation, and desktop/process changes. Prove that disabled terminal/tunnel/camera/unapproved file/public-fallback paths cannot bypass product admission. Determine the actual authenticated direct-LAN transport; do not assume upstream ID-server configuration supplies our organization authority.
3. **Preview/detail coexistence:** request a low-cost overview and high-quality detail view of the same computer from different operators. Measure whether source capture, scaling, encoding, bandwidth, and decoding stay bounded, and whether quality changes affect other viewers. If separate stream renditions require patches, record their exact extent rather than treating custom FPS or a smaller native view as proof.
4. **Platform/load and maintenance decision:** exercise both Mac architectures and all promised manager/endpoint combinations, multiple displays and input layouts; measure 30 then 60 actual endpoint previews, slow/offline receivers and presentation fan-out. Record reproducible builds, required upstream patches, update strategy, and license inventory. Adopt only if the resulting maintenance and measured behavior meet E01/E04/E06 and the system invariants.

The product interface should express admitted observation demand, preview/detail intent, display identity, frame lifetime, admitted input, and stop/error events. Actual ABI names and protocol fields come from these experiments under E03. Accounts, enrollment, groups, server file jobs, and native UI remain product-owned. A thin interface does not make an upstream replacement inexpensive; the experiment must measure how deep the required fork becomes.

If RustDesk fails the native/admission/preview/maintenance gates, evaluate a VNC/RFB route using existing protocol libraries and separately proven Mac/Windows capture/input adapters. That route needs its own authenticated encrypted transport, authorization, native rendering, performance and license proofs. VNC is not automatically too slow, and video codecs are not automatically efficient for dozens of mostly static previews. Compare text editing, scrolling and motion on the same reference hardware before selecting a fallback. Implementing every codec, protocol, and platform edge from scratch is not the proposed fallback.

## Contradiction and assumption checks

**Native apps versus RustDesk UI:** RustDesk's existing desktop UI does not meet the native UI constraint. The presence of Rust library outputs makes a native adapter plausible, not proven. The plan explicitly excludes treating a reskin as fulfillment.

**Self-hosted relay versus management server:** The upstream rendezvous/relay roles are different from classroom enrollment, teacher authorization, lessons, and school configuration. The plan does not conflate them.

**One-to-one remote desktop versus classroom media:** No reviewed source established a cheap 60-device grid or efficient shared presentation fan-out through a native adapter. Both remain adoption gates.

**Agent installed versus desktop observable:** Mac privacy permissions and Windows user-session separation can prevent capture while a device is otherwise online. Capability reporting and onboarding must reflect that distinction.

**Easy hosting versus examples with broad host changes:** Official installation examples include broad setup commands and optional WebSocket listeners. They are deployment examples, not a suitable noninterference contract for this product. The proposed wizard reviews only the product's required changes.

**Encryption versus authority:** Source marketing claims do not prove the future product's session binding, grant validation, or compromise recovery. The plan requires inspecting and testing the adopted handshake; the security model is a design recommendation.
